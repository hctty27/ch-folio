# 多人第二阶段：服务端权威车辆物理设计

## 状态

- 设计已由用户确认。
- 本文只定义架构、协议、确定性约束、失败处理、性能门槛与验收标准。
- 本阶段尚未开始实现。

## 1. 目标

在现有基于房间的多人 MVP 上增加服务端权威车辆物理，使同一房间内最多 8 名玩家看到唯一、可复现的车辆碰撞结果，包括正面对撞、追尾、侧撞、翻滚、撞飞和多车叠压。

客户端继续保持即时驾驶响应，但不再以客户端上传的位置作为权威来源。客户端只上传量化后的驾驶输入；服务端运行唯一的 Rapier 物理世界并广播权威状态。客户端通过全房间预测、回滚和重放收敛到服务端结果。

“双方一致”定义为：双方最终使用相同的权威位置、旋转、线速度、角速度、车辆控制器状态和碰撞结果。由于网络延迟不同，不要求两台设备在现实时间的同一毫秒显示完全相同的帧。

## 2. 非目标

本阶段不包含：

- 账号系统、数据库档案或长期车辆持久化；
- 匹配队列、房间浏览器、语音或文字聊天；
- 车辆损伤、零件脱落或可破坏场景；
- 服务端渲染或录像系统；
- 反作弊的完整行为分析；
- 超过 8 人的兴趣区域或分片；
- 普通无 `room` 参数页面的多人连接。

## 3. 已确定的核心参数

| 项目 | 配置 |
|---|---|
| 房间最大玩家数 | 8 |
| 服务端权威物理 | 60 Hz，固定 `1 / 60s` 时间步 |
| 客户端预测 | 60 Hz，预测房间内全部车辆 |
| 服务端输入缓冲 | 3 tick，约 50 ms |
| 权威状态广播 | 20 Hz |
| 完整物理检查点 | 30 Hz |
| 客户端回滚历史 | 1 秒：30 份世界检查点、60 tick 输入 |
| 车辆 CCD | 开启 |
| `maxCcdSubsteps` | 2 |
| 全局求解迭代 | 4 |
| 内部 PGS 迭代 | 1 |
| 每台车辆附加求解迭代 | 2 |
| 车辆碰撞体 | 3–5 个凸形组成复合车身 |
| 静态权威地图 | 地面、主要墙体、护栏、关键坡道和大型障碍物 |
| 断线宽限期 | 3 秒 |
| 缺失输入保持期 | 6 tick，约 100 ms |
| 状态校验 | 20 Hz 轻量 checksum、1 Hz 完整世界哈希 |

## 4. 总体架构

```text
浏览器客户端
├── 输入量化与发送
├── 60 Hz 全房间预测世界
├── 30 Hz Rapier 世界检查点
├── 1 秒输入/回滚历史
├── 权威状态校验与回滚重放
└── Three.js 视觉校正
             │
             │ 固定二进制 WebSocket 协议
             ▼
Cloudflare Worker 路由层
             │ room -> Durable Object
             ▼
GameRoom Durable Object
├── WebSocket 会话与恢复令牌
├── 3 tick 输入缓冲
├── 60 Hz 唯一权威物理世界
├── 20 Hz 权威广播
├── 加入、出生、断线与重连状态机
├── 性能监控与同步诊断
└── 平台适配器
             │
             ▼
平台无关权威物理核心
├── 共享车辆参数
├── 精简静态碰撞地图
├── 固定 tick 输入消费
├── Rapier 世界推进
├── 规范状态编码与校验
└── 快照/恢复接口
```

权威物理核心不得直接依赖 Cloudflare 的 `DurableObjectState`、WebSocket API、存储 API 或 Node.js 网络 API。平台层仅负责：

- 连接与房间生命周期；
- 单调 tick 调度；
- 接收和批处理输入；
- 广播协议帧；
- 指标采集；
- 生成安全随机令牌。

若 Durable Object 压测不达标，相同物理核心将由 Node.js 权威服务器适配器运行，客户端协议与回滚系统不重写。

## 5. 确定性约束

客户端预测、Durable Object 权威端和未来 Node.js 权威端必须满足以下不变量：

1. 使用完全相同的 Rapier 精确版本，不允许 `^` 或 `~` 浮动范围。
2. 使用相同的固定时间步、CCD、求解迭代和车辆控制器设置。
3. 按服务端分配的稳定 `entityOrder` 创建和删除车辆、刚体、碰撞体及控制器。
4. 复合车身碰撞体按固定数组顺序创建。
5. 每个 tick 按稳定的 `entityOrder` 处理所有玩家输入，再调用车辆控制器，再推进世界。
6. 所有物理输入先量化，再同时用于本地预测和服务端模拟。
7. 物理核心不得使用墙钟时间决定模拟结果。
8. 不在确定性路径中使用跨平台结果可能不同的三角函数或随机数；必要常量预计算并写入共享配置。
9. 地图碰撞数据使用版本化、稳定排序的生成产物，不在运行时依赖对象遍历顺序。
10. Three.js 的视觉平滑绝不写回 Rapier 世界。

版本握手包含：

```text
protocolVersion = 2
vehiclePhysicsVersion = 1
mapCollisionVersion = 1
```

任一版本不一致时，服务端拒绝进入权威房间。版本号后续按不兼容变化递增。

## 6. 共享车辆物理配置

当前驾驶手感作为基线。实施时把现有客户端车辆参数抽取为平台无关共享配置，包括：

- 车身质量、重心和惯性相关参数；
- 底盘阻尼、空气阻力和最大速度策略；
- 四轮连接点、前后轮距和轴距；
- 车轮半径；
- 悬挂静止长度、最大行程、刚度、压缩阻尼、回弹阻尼；
- 轮胎抓地、侧向摩擦和最大悬挂力；
- 发动机力、制动力、手刹和最大转向角；
- 前进轴、上轴和轮轴方向；
- CCD 和附加求解迭代设置；
- 复合车身碰撞体定义。

每台车使用一个动态底盘刚体，附着 3–5 个凸形或长方体碰撞体，例如：

1. 低矮主底盘；
2. 前舱；
3. 乘员舱；
4. 后舱；
5. 可选底部防穿透形状。

不使用 SU7 视觉三角网格作为动态碰撞体。

## 7. 精简静态碰撞地图

服务端权威地图仅包含会显著改变车辆轨迹或撞飞结果的结构：

- 地面和主要可行驶表面；
- 建筑主体墙面；
- 道路边界、护栏和不可穿越边界；
- 关键坡道、台阶、跳台；
- 大型固定障碍物。

不包含纯装饰、小型道具、植被细节或不会影响车辆轨迹的视觉网格。

生成策略：

- 大面积不规则地面可使用固定三角网格；
- 墙体、护栏和坡道优先用长方体或凸形；
- 所有碰撞体写入独立、版本化的静态数据文件；
- 生成器输出稳定 ID、稳定排序和内容哈希；
- 客户端预测端与权威端加载同一份产物。

## 8. 输入协议与缺失输入规则

客户端不上传车辆坐标。每个输入包使用固定小端二进制布局，至少包含：

```text
messageType       uint8
protocolVersion   uint16
clientTick        uint32
inputSequence     uint32
throttle          uint8
brake             uint8
steering          int16
flags             uint8
```

输入量化规则必须在共享模块中实现。键盘、手柄或触摸输入先转换为统一浮点语义，再量化；本地预测和网络发送使用同一个量化结果。

服务端权威时间线比实时落后 3 tick。每个权威 tick：

1. 按稳定玩家顺序读取该 tick 的输入；
2. 若输入尚未到达，使用确定性缺失输入规则；
3. 更新全部车辆控制器；
4. 推进 Rapier 世界一次；
5. 记录权威状态、性能数据和待广播事件。

缺失输入规则：

```text
缺失 0–6 tick：沿用最后一次有效输入
缺失超过 6 tick：
- 油门立即归零
- 转向在后续 6 tick 线性回正
- 刹车在后续 6 tick 线性提升至 1
```

超过服务端 3 tick 缓冲窗口才到达的输入直接丢弃，不回改已经确认的服务端历史。

## 9. 权威状态协议

20 Hz 权威状态包使用固定二进制布局，并按稳定 `entityOrder` 编码车辆。每辆车至少包含：

```text
playerId / entityOrder
position          float32 × 3
quaternion        float32 × 4
linearVelocity    float32 × 3
angularVelocity   float32 × 3
steering/wheel/control state
collision/airborne/roll flags
lastConfirmedInputSequence
```

包头包含：

- `serverTick`；
- 三项版本号；
- 房间实体数量；
- 车辆规范状态 `checksum32`；
- 可选的 1 Hz 完整世界哈希；
- 出生、删除、会话恢复等确定性事件。

普通 20 Hz 包不携带完整 Rapier 世界快照。完整快照只用于：

- 新玩家中途加入；
- 权威 tick 超出客户端 1 秒回滚窗口；
- 连续不同步；
- 完整世界哈希不一致；
- 断线恢复后的硬同步；
- 诊断和故障恢复。

## 10. 客户端全房间预测与回滚

每个客户端本地维护与服务端结构相同的预测物理世界，并模拟房间内全部车辆。

保存内容：

- 30 Hz 的完整 Rapier 世界检查点，共 30 份；
- 60 Hz 的全玩家量化输入，共 60 tick；
- 每个 tick 的玩家—实体映射；
- 项目级车辆控制器元数据；
- 服务端 tick 与输入确认序号；
- 规范状态校验值。

收到权威 tick `T` 后：

1. 验证协议和物理版本；
2. 比较本地预测状态与权威状态；
3. 找到 `T` 或 `T` 之前最近的完整检查点；
4. 恢复 Rapier 世界；
5. 恢复项目级实体映射和控制器元数据；
6. 写入 tick `T` 的权威车辆状态；
7. 按稳定顺序重放 `T` 之后的全部量化输入；
8. 追赶至当前预测 tick；
9. 计算视觉校正偏移；
10. 丢弃已确认且超出窗口的历史。

检查点为 30 Hz，因此从最近检查点定位到任意权威 tick 最多额外重放 1 个 tick；随后仍需重放尚未确认的输入。

若 `T` 早于 1 秒历史窗口，放弃局部回滚并请求完整权威同步。

## 11. 视觉校正

Rapier 物理状态在回滚后立即采用权威结果。Three.js 车辆模型使用独立视觉偏移进行分级收敛：

| 误差 | 视觉处理 |
|---|---|
| 位置 `< 0.25m` 且旋转 `< 5°` | 100 ms 内平滑消除 |
| 位置 `0.25–1.5m` 或旋转 `5–25°` | 50 ms 内快速收敛 |
| 位置 `> 1.5m`、旋转 `> 25°`、新权威碰撞、翻滚或叠压 | 立即显示回滚结果 |

视觉状态仅影响渲染，不参与碰撞、轮胎射线或下一 tick 输入计算。

## 12. 中途加入与安全出生

房间最多保留 8 个玩家槽位。活动玩家、同步中的玩家和处于 3 秒断线宽限期的玩家都占用槽位。

新玩家加入流程：

1. 建立 WebSocket 并校验三项版本；
2. 分配 `playerId`、稳定 `entityOrder` 和会话槽位；
3. 以同步中状态加入，不创建车辆刚体；
4. 服务端在权威 tick `T` 生成完整世界快照；
5. 附带玩家—实体映射、控制器元数据以及 `T` 之后的输入；
6. 新客户端无渲染恢复并快速重放到当前 tick；
7. 客户端发送 `sync_ready`；
8. 服务端按编号 `0 → 7` 检查固定出生位；
9. 若无安全位置，玩家保持“等待安全出生位置”；
10. 在确定的未来 tick 广播 `spawn` 并创建车辆；
11. 所有客户端按相同事件顺序创建实体；
12. 出生完成后开放驾驶输入。

出生位安全条件：

- 膨胀后的车身形状不与其他车辆相交；
- 保留配置化安全边距；
- 附近没有会在短时间内高速进入出生区域的车辆；
- 地面接触与初始姿态有效。

服务端以 20 Hz 重新检查出生位。所有位置不安全时无限等待，不强制叠车，不引入无碰撞保护。

## 13. 断线、恢复与会话令牌

连接断开后，权威车辆保留 3 秒：

- 油门归零；
- 转向按确定性规则回正；
- 刹车升至 1；
- 车辆继续参与权威碰撞；
- 玩家槽位继续占用。

首次加入时，服务端生成 256-bit 随机 `resumeToken`：

- 客户端原始令牌只存入 `sessionStorage`；
- 令牌不放入 URL 查询参数；
- 服务端仅保存摘要；
- WebSocket 建立后的首个恢复消息携带 `playerId` 和令牌；
- 校验使用固定时间比较；
- 成功恢复后立即轮换令牌，旧令牌作废；
- 同一车辆只允许一个活动连接；
- 新连接接管成功后，旧连接不能再次获得控制权。

3 秒内恢复时发送完整权威同步并接管原车辆。超过 3 秒时，服务端在固定 tick 删除车辆、释放槽位并广播 `despawn`。

## 14. 不同步检测与恢复

两级校验：

1. 每个 20 Hz 权威状态包计算车辆规范状态 `checksum32`，覆盖车辆顺序、位置、旋转、速度、控制器状态和确认输入序号。
2. 每 60 tick 对完整 Rapier 世界快照计算强哈希，检测接触缓存和求解器等隐藏状态分叉。

处理规则：

| 状况 | 处理 |
|---|---|
| 单次轻量校验不一致 | 正常回滚并重放 |
| 连续 3 次轻量校验不一致 | 请求完整权威同步 |
| 1 Hz 完整世界哈希不一致 | 立即硬同步并记录诊断 |
| 权威 tick 超出 1 秒窗口 | 硬同步 |
| 硬同步后仍不一致 | 断开并提示物理环境或版本不兼容 |

诊断记录至少包含：

- 房间、服务端 tick、玩家数量；
- 三项版本号和 Rapier 精确版本；
- 最近输入序列范围；
- 本地与权威 checksum/hash；
- 回滚次数和重放 tick 数；
- 最近碰撞/出生/删除事件；
- tick 性能分解。

## 15. Durable Object 运行策略与迁移边界

首版在现有 `GameRoom` Durable Object 中运行权威物理原型。只要房间存在活动、同步中或宽限期玩家，60 Hz 物理计时器保持对象在内存中。最后一个槽位释放后：

- 立即停止 tick 调度；
- 释放 Rapier 世界、检查点和输入历史；
- 保留必要的持久房间元数据；
- 允许对象重新满足休眠条件。

高频输入与状态尽量批处理，目标每 50 ms 发送一帧服务端状态，并在客户端输入侧将多个逻辑输入合并到少量 WebSocket 帧，降低消息上下文切换开销。

物理核心暴露平台无关接口，例如：

```text
createWorld(config, mapData)
addPlayer(playerDescriptor)
removePlayer(entityOrder)
applyInputs(tick, orderedInputs)
step()
takeCheckpoint()
restoreCheckpoint(bytes, metadata)
readCanonicalState()
computeChecksum()
```

Cloudflare 适配器和未来 Node.js 适配器只实现调度、网络、令牌和监控。

## 16. 性能验收与迁移判定

Durable Object 原型必须通过以下硬门槛：

```text
8 台车连续高强度碰撞压测：10 分钟

物理 tick：
p95 ≤ 8 ms
p99 ≤ 12 ms
最大单 tick ≤ 16.67 ms

内存：
观察到的峰值 ≤ 96 MB

网络与稳定性：
20 Hz 权威状态无持续积压
输入队列不超过 3 tick 缓冲
无房间重启
无异常 WebSocket 断开
无持续 checksum/hash 分叉
```

性能采集应区分：

- 输入解码；
- 车辆控制器更新；
- broad phase；
- narrow phase；
- CCD；
- solver；
- 世界快照；
- checksum/hash；
- 状态编码与广播。

全部满足则继续使用 Durable Object。任一核心指标在稳定负载下持续不满足，则将权威物理迁移至专用 Node.js 服务器；Cloudflare 保留房间入口、路由、健康检查或连接分配职责。

## 17. 测试策略

### 17.1 纯函数与协议测试

- 输入量化边界、饱和和往返编码；
- 固定二进制字段偏移、长度和小端序；
- 版本不一致拒绝；
- 缺失输入 6 tick 保持与后续安全输入；
- 3 tick 服务端缓冲和迟到输入丢弃；
- 规范状态排序和 checksum 稳定性；
- resumeToken 轮换和旧令牌失效。

### 17.2 确定性测试

同一初始快照和输入日志分别在：

- 浏览器预测核心；
- Worker 测试环境；
- Node.js 适配器测试环境；

运行相同 tick 数，要求：

- 20 Hz 规范状态完全一致；
- 1 Hz 完整世界快照哈希一致；
- 实体创建、出生和删除顺序一致。

### 17.3 回滚与网络仿真

模拟：

- 0–300 ms 延迟；
- 抖动；
- 输入乱序；
- 丢包和批量到达；
- 超过 1 秒的迟到权威状态；
- 临时断线和 3 秒内恢复。

验证预测世界最终收敛、回滚窗口正确裁剪、硬同步路径可恢复。

### 17.4 物理场景测试

至少覆盖：

- 两车低速正碰；
- 两车高速正碰；
- 追尾；
- 侧撞；
- 斜向挤压；
- 护栏撞击；
- 坡道腾空与落地；
- 翻滚和车顶接触；
- 4–8 车连续碰撞与叠压；
- 高速 CCD 防穿透；
- 出生位占用与等待。

每个场景使用固定输入日志和预期权威哈希。

### 17.5 性能测试

建立可重复的 8 车压力脚本，持续 10 分钟，输出 p50/p95/p99/max tick、Rapier 阶段分解、快照和编码耗时、内存峰值、队列深度与断连数。

## 18. 上线与兼容策略

第二阶段协议与第一阶段状态上传协议不兼容，因此升级为 `protocolVersion = 2`。旧客户端不得进入第二阶段权威房间。

上线顺序：

1. 共享配置、物理核心和离线确定性测试；
2. 二进制协议与 Worker 权威循环；
3. 客户端全房间预测和回滚；
4. 加入、出生、断线和恢复；
5. 精简地图生成；
6. 端到端碰撞测试；
7. Durable Object 8 车压力测试；
8. 根据硬门槛决定继续 Cloudflare 或迁移 Node.js；
9. 最后才在生产 `?room=` 房间启用协议 v2。

普通地址 `https://ch.testnb.me/` 继续严格单人，不建立多人 WebSocket。只有有效 `?room=<name>` 才进入多人握手。

## 19. 验收标准

- 同房间两台车高速正面对撞后，双方最终位置、旋转、线速度和角速度一致。
- 追尾、侧撞、翻滚、撞飞和多车叠压由服务端唯一裁决。
- 本地驾驶不等待服务器确认，输入即时生效。
- 网络抖动允许视觉校正，但不会永久分叉。
- 权威状态超出回滚窗口时能完成硬同步。
- 中途加入不会暂停现有玩家。
- 没有安全出生位时玩家等待，不发生强制叠车。
- 3 秒内断线恢复原车辆并轮换令牌；超时后确定性删除车辆。
- 版本不一致客户端被明确拒绝。
- 无参数地址始终为单人模式。
- Durable Object 只有在通过既定 8 车性能门槛后才作为正式权威物理宿主；否则使用预留的 Node.js 迁移路径。
